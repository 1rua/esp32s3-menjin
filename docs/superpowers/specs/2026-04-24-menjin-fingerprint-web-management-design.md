# 门禁固件指纹 Web 录入与管理设计

- 日期：2026-04-24
- 目标工程：`esp32-s3-menjin-version3.0`
- 主文件：[`esp32-s3-menjin-version3.0.ino`](../../../../esp32-s3-menjin-version3.0/esp32-s3-menjin-version3.0.ino)
- 相关模块：[`fingerprint_access/`](../../../../esp32-s3-menjin-version3.0/fingerprint_access/), [`web_portal/`](../../../../esp32-s3-menjin-version3.0/web_portal/)

## 1. 背景

当前指纹能力已经从主草图中抽离到 [`fingerprint_access`](../../../../esp32-s3-menjin-version3.0/fingerprint_access/) 模块，但仍然保留了较早期的交互模型：

- 录入入口仅支持串口 `E/e` 触发
- 录入流程仍是偏原始的双次采样状态机
- Web 门户尚未提供指纹列表、删除、命名、录入进度等管理能力

这带来三个现实问题：

1. 普通用户无法在不接串口的情况下完成指纹录入
2. 设备侧无法对“已有指纹模板”做可视化管理
3. 当前双次录入对落点和角度变化的容错有限，不够接近手机式多次采样体验

本次设计目标是在保持现有本地门禁、OTA、配网、MQTT、NFC、键盘和 Web 控制台整体结构不被打乱的前提下，为指纹子系统增加 Web 驱动的录入与管理能力，并把录入状态暴露给 Web 页面进行简单百分比进度展示。

## 2. 目标与非目标

### 2.1 目标

- 支持通过 Web 页面发起新的指纹录入
- 支持 Web 页面查看已录入指纹列表
- 支持 Web 页面为已有指纹命名和重命名
- 支持 Web 页面删除已有指纹
- 将现有双次录入升级为 4 次采样的多阶段录入与交叉验证流程
- 支持 Web 页面通过简单百分比进度条查看录入进度
- 保留串口 `E/e` 作为备用录入入口，但与 Web 共用同一套录入状态机
- 保持主草图继续只承担装配和顶层编排职责

### 2.2 非目标

- 不引入 WebSocket、SSE 或其它推送式前端技术
- 不新增批量清空全部指纹的能力
- 不在本期支持多个并行录入会话
- 不重写当前 Web 门户整体页面风格
- 不引入新的框架层、事件总线或 RTOS 任务
- 不在本期做“开机扫描传感器全部模板并自动重建元数据”的恢复能力

## 3. 需求定稿

本次需求按以下约束固定：

- Web 端“管理已有指纹”范围为：**列表 + 删除 + 命名**
- Web 发起录入时，指纹 ID 采用：**自动分配空闲槽位**
- 新录入流程采用：**4 次采样**
- 录入进度展示方式采用：**简单百分比进度条**
- 现有串口 `E/e` 触发入口：**保留为备用入口**

## 4. 总体方案

采用 **单一录入会话状态机 + Web 轮询进度** 的方案。

整体依赖关系如下：

1. [`fingerprint_access`](../../../../esp32-s3-menjin-version3.0/fingerprint_access/) 负责：
   - 指纹传感器初始化
   - 指纹匹配开门查询
   - 指纹录入会话状态机
   - 指纹元数据列表管理
   - 自动分配空闲指纹 ID
   - 删除模板与元数据
   - 导出录入状态给 Web 层

2. [`web_portal`](../../../../esp32-s3-menjin-version3.0/web_portal/) 负责：
   - 提供指纹管理的 HTTP API
   - 在现有控制台页面新增“指纹管理”区块
   - 轮询录入状态接口并渲染百分比进度条

3. 主草图 [`esp32-s3-menjin-version3.0.ino`](../../../../esp32-s3-menjin-version3.0/esp32-s3-menjin-version3.0.ino) 继续只保留：
   - `tickFingerprintAccess(...)`
   - `pollFingerprintMatch(...)`
   - Web 回调桥接函数
   - 串口 `E/e` 到统一录入入口的薄适配

该方案刻意避免让 Web 层直接持有指纹传感器细节，也避免为串口和 Web 维护两套录入逻辑。

## 5. 指纹模块边界调整

当前 [`fingerprint_access.h`](../../../../esp32-s3-menjin-version3.0/fingerprint_access/fingerprint_access.h) 只暴露了初始化、串口输入处理、录入 tick、匹配查询等基础接口。本次需要将它扩展为“识别 + 管理 + 录入会话”的统一模块。

### 5.1 保留职责

- 指纹传感器初始化
- 指纹匹配查询
- 串口触发入口支持

### 5.2 新增职责

- 指纹元数据持久化与列表导出
- Web 触发录入
- Web 查询录入状态
- Web 取消录入
- 删除指纹模板
- 重命名指纹记录
- 自动分配下一个空闲 ID

### 5.3 不新增职责

- 不直接控制门锁开门
- 不直接渲染 Web 页面
- 不在模块内发起 HTTP 响应

## 6. 录入算法设计

### 6.1 会话模型

同一时刻只允许一个录入会话。录入会话由以下信息组成：

- 录入来源：`Web` 或 `Serial`
- 目标指纹 ID
- 待保存名称
- 当前阶段
- 已完成采样数
- 总采样数（固定为 4）
- 当前提示文本
- 当前百分比
- 最近错误信息
- 会话是否可取消

### 6.2 4 次采样流程

录入固定采用 4 次采样，每次都需要“按下 -> 成功采样 -> 抬起”这一完整动作：

1. **第 1 次采样**：采集第一个特征模板
2. **第 2 次采样**：采集第二个特征模板，并完成基础一致性检查
3. **第 3 次采样**：作为交叉验证样本，验证与前两次是否一致
4. **第 4 次采样**：再次做交叉验证，确认稳定后再执行最终提交

实现机制在本期明确固定为：

- 第 1、2 次采样成功后，先执行一次 `createModel`
- 生成的模型先以 **临时已写入、未最终确认** 的状态存入自动分配的目标 ID
- 第 3、4 次采样都通过 `image2Tz + fingerFastSearch` 或等价搜索路径，要求命中的模板 ID 必须等于当前会话目标 ID
- 如果第 3 或第 4 次验证失败，则立即删除该目标 ID 上的临时模型并结束会话
- 只有第 4 次验证成功后，才写入对应元数据并把会话标记为完成

设计动机不是把底层模板真的扩展成 4 份长期存储，而是通过额外采样提高同一根手指在不同角度、不同落点下的一致性置信度。

### 6.3 进度定义

Web 端进度条只展示百分比，但设备侧需要输出稳定、可解释的进度值：

- 会话创建成功：`0%`
- 第 1 次采样成功：`25%`
- 第 2 次采样成功：`50%`
- 第 3 次交叉验证成功：`75%`
- 第 4 次交叉验证成功且模板写入完成：`100%`

同时，状态接口返回一条短提示文案，例如：

- `请放置手指（1/4）`
- `请移开手指`
- `请换一个角度再次按压（3/4）`
- `正在验证并写入模板`
- `录入完成`
- `录入失败：第 3 次采样与前序特征不一致`

### 6.4 失败与重试策略

为了保证状态机可控，本期采用有限重试策略：

- 每个采样阶段允许 **1 次瞬时重试**，用于处理图像质量差或短暂抖动
- 同一阶段连续失败则整个会话失败
- 会话失败后由用户重新发起，不自动无限重试
- 会话失败、取消或完成后都必须清空会话状态

## 7. 元数据设计

指纹模板本身由传感器内部存储管理，但 Web 展示和管理不能只依赖传感器内部状态。因此 ESP32 侧需要维护一份轻量元数据索引。

建议新增固定数组风格的元数据结构，字段至少包括：

- `id`：指纹模板 ID
- `name`：指纹名称
- `occupied`：该条目是否已占用

本期不引入额外元数据字段，明确只保留 `id + name + occupied`。

### 7.1 存储方式

沿用当前工程风格，使用 [`Preferences`](../../../../esp32-s3-menjin-version3.0/access_control/access_control.h) 存储固定数组：

- `fp_meta_cnt`
- `fp_meta_list`

### 7.2 一致性策略

本期采用 **“以 NVS 元数据为准”** 的简单一致性策略：

- 新录入成功时，同时写入传感器模板和元数据
- 删除成功时，同时删除传感器模板和元数据
- 如果出现“传感器里存在模板但元数据缺失”的历史不一致情况，本期不做开机全量扫描修复
- 如果运行中发现 ID 冲突或删除失败，则返回错误给 Web

### 7.3 名称约束

名称约束在本期固定为：

- 去除首尾空白后不能为空
- 最大长度为 24 个可见字符
- 超长请求直接返回 400，不做自动截断

## 8. Web API 设计

沿用当前 [`web_portal.cpp`](../../../../esp32-s3-menjin-version3.0/web_portal/web_portal.cpp) 的 JSON 路由风格，新增以下接口：

### 8.1 `GET /fingerprints`

返回已录入指纹列表。

#### 返回字段

- `items`: 数组
  - `id`
  - `name`
  - `occupied`

### 8.2 `POST /fingerprint_enroll_start`

发起新的录入会话。

请求参数：

- `name`

返回字段：

- `id`
- `name`
- `progress`
- `phase`
- `message`

### 8.3 `GET /fingerprint_enroll_status`

查询当前录入会话状态。

返回字段：

- `active`
- `id`
- `name`
- `progress`
- `step`
- `totalSteps`
- `phase`
- `message`
- `error`

### 8.4 `POST /fingerprint_enroll_cancel`

取消当前录入会话。

### 8.5 `POST /fingerprint_rename`

修改已有指纹名称。

请求参数：

- `id`
- `name`

### 8.6 `POST /fingerprint_delete`

删除已有指纹。

请求参数：

- `id`

行为要求：

- 删除传感器模板
- 删除对应元数据

## 9. Web 页面设计

在当前控制台页面 [`CONTROL_PAGE_HTML`](../../../../esp32-s3-menjin-version3.0/web_portal/web_portal.cpp#L9-L331) 中新增一个“指纹管理”卡片。

### 9.1 UI 范围

该卡片只承担以下职责：

- 展示已有指纹列表
- 输入新名称并发起录入
- 显示当前录入进度条
- 显示当前录入提示文本
- 对已有指纹执行重命名
- 删除已有指纹
- 取消当前录入

### 9.2 前端交互方式

采用短轮询，不采用推送：

- 用户点击“开始录入”后，前端启动轮询
- 每 `500ms ~ 1000ms` 请求一次 `/fingerprint_enroll_status`
- 当录入完成、失败或取消时，停止轮询
- 录入结束后自动刷新指纹列表

### 9.3 进度条

进度展示仅需要简单百分比条：

- 宽度按 `progress` 百分比变化
- 旁边显示文本状态
- 不做复杂动画
- 不做多阶段可视化图谱

## 10. 串口入口兼容策略

现有串口 `E/e` 入口继续保留，但不再维持独立录入逻辑，而是改为调用统一录入会话入口。

行为约束如下：

- 串口和 Web 共用同一个录入状态机
- 如果当前已有录入会话，串口再次触发应直接拒绝
- 串口触发时如果没有显式名称，可使用默认命名策略，例如 `Fingerprint <ID>`
- 后续仍可在 Web 页面中修改该名称

这样可以保留调试入口，又避免维护两套状态机。

## 11. 冲突规则

为避免运行时状态混乱，以下规则固定：

- 同一时刻只允许 1 个录入会话
- 录入进行中时，暂停指纹匹配开门
- 录入进行中时，禁止再次发起录入
- 录入进行中时，禁止删除指纹
- 录入进行中时，允许查看列表和查看进度
- 录入进行中时，第一版建议禁止改名，以降低并发状态复杂度
- 以下状态下禁止启动录入：
  - OTA 中
  - 配网门户激活中
  - 指纹传感器未就绪
  - 指纹 ID 已满
  - 名称为空或超长

## 12. 错误处理设计

### 12.1 启动前错误

- 传感器未连接
- 正在 OTA
- 正在配网门户
- 已有录入任务进行中
- 指纹库存已满
- 名称为空或超长

### 12.2 采样阶段错误

- 长时间未放置手指
- 长时间未移开手指
- 图像质量差
- 第 2/3/4 次采样与前序特征不一致

### 12.3 写入阶段错误

- `createModel` 失败
- `storeModel` 失败
- 理论上不该发生的目标 ID 冲突

### 12.4 管理阶段错误

- 改名目标不存在
- 删除目标不存在
- 删除传感器模板失败
- 元数据保存失败

### 12.5 清理原则

- 会话取消、失败、完成后都要清理会话状态
- 如录入中产生临时占用状态，应在失败路径回滚
- 状态接口保留最近一次失败信息，直到下一次会话创建

## 15. 风险与约束

### 15.1 传感器底层能力限制

Adafruit 指纹库的底层建模流程并不是为“手机式连续多样本训练”设计的，因此 4 次采样实现更接近“2 次建模 + 2 次交叉一致性验证”，而不是消费级手机传感器那种真正多轮渐进学习模型。该差异需要在实现中接受，不应在本期追求不可达的底层能力。

### 15.2 状态机膨胀风险

如果把 Web、串口、元数据、传感器健康、错误恢复全部混在一个大函数里，`fingerprint_access.cpp` 会快速膨胀。因此实现时必须先把：

- 元数据子层
- 录入会话子层
- 传感器原语调用子层

在代码结构上明确分段，即使先放在同一个 `.cpp` 文件里，也要边界清晰。

### 15.3 一致性风险

本期不做开机全量模板扫描，因此若用户通过外部工具直接改动传感器模板，ESP32 侧元数据可能失真。本期将其视为超出范围的异常场景。

## 16. 结论

本设计确定采用以下组合：

- **方案**：单会话状态机 + Web 轮询进度
- **管理范围**：列表 + 删除 + 命名
- **ID 分配**：自动分配空闲槽位
- **录入强度**：4 次采样
- **进度展示**：简单百分比进度条
- **串口入口**：保留为备用入口，但与 Web 共用同一状态机

该方案能够在不引入额外框架、不打乱当前模块边界的前提下，把指纹子系统从“仅串口调试功能”提升为“可通过 Web 管理的正式门禁能力”，并为后续继续扩展指纹 UI 或更强的一致性策略留出空间。
